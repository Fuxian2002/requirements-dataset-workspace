版本：1.0　｜　编制日期：2026-10-10　｜　执行对象：Codex

## 0. 任务摘要：先读这一页

请对 NASA 的 LC（Limit Checker）项目，完成一套“需求整理与补全 → 系统资源整理与补全 → SpaceRDL 规约转换 → 追踪与检查”的交付物，最终打包为 `lc_spacerdl.zip`，供用户交回独立审查。

**本任务不是修改 LC 功能，不是修复 LC 代码，也不是把所有 C 函数逐个翻译成 SpaceRDL。**目标是整理清楚“LC 被要求做什么、实际代码补充说明了什么、需要哪些资源、这些内容怎样用 SpaceRDL 表达”。

### 已确定的工作原则

1. **保留从代码补充需求的工作。**负责人认可这一过程；不能因为需求文档没写，就忽略代码中有依据的重要行为。
2. **主动补全资源信息。**资源缺失是转换工作的组成部分，不应只留下若干资源名称就宣布完成。
3. **重点纠正语法理解。**尤其核对 `Compute` 的参数，以及 `ReqCapByTable` / `ReqCapByFormTable` 的写法和使用范围。SMART-QSO 的 ZIP 是组织方式参考，不是语法标准。
4. **来源与状态必须透明。**从代码得到的内容要标明是代码补充；文档与代码不一致时保留双方，不能把实现自动升级为正确的原始要求。
5. **所有结论可追溯。**交付包必须让另一位审查者找到原始材料、资源定义、语句和检查依据。

最终保留 SMART-QSO 示例中的七个主文件：`README.md`、`requirements.md`、`resources.md`、`statements.md`、`code.rdl`、`traceability.md`、`issues.md`。另外附上必要的语法说明、来源清单、检查报告和一个贯通例子，具体见第 8 节。

**不要预设 LC 应有 66 条需求、31 条语句或 40 个问题。这些是旧项目的数字，不是本任务指标。**

本交接文档中的内容分为三种依据：负责人反馈、用户提供的 SpaceRDL 材料、为本次交付新增的执行与验收规则。新增的编号、状态分类、目录和检查要求，不是 NASA 或论文原本规定的格式。

## 2. 首先确定 LC 的分析边界与版本

### 2.1 基线选择

优先使用用户明确指定的版本。没有指定时，选择能够同时取得需求、设计说明和源码的官方版本，并记录选择理由；不要为了“最新”牺牲资料可对齐性。

必须记录仓库地址、tag/分支、完整 commit SHA、获取时间、相关依赖版本或未知项。对独立下载的 PDF、CSV、发布附件，记录原始地址、文件名、版本信息和 SHA-256。只有分支名没有 commit，不足以固定基线。

若只有历史需求与较新代码，分别标记“需求基线”和“实现基线”，把跨版本差异单列，不能把它们伪装成同版冲突。历史用户指南必须核对其适用版本。

### 2.2 只分析相关边界，不把 LC 变成整颗卫星

以 LC 应用及其直接交互为主要范围。先区分 LC 内部状态和算法、框架提供的通信或表管理能力、外部应用承担的命令执行，以及部署配置。

**LC 发出启动请求，不等于外部脚本已经执行成功，更不等于被监测的异常已经消除。**成功条件应停在有证据支持的边界，除非另有回执或后续状态证据。

下面只是阅读导航，需在选定基线逐项确认，不是已经完成的 LC 分析结论：

- 指令校验、状态改变、统计复位和运行状态报告。
- Watchpoint：数据选取、比较、结果、统计和时效。
- Actionpoint：评估请求、表达式、结果、连续计数及动作条件。
- 表定义、更新与验证；初始化、复位及状态恢复。

公开需求中 `LC2003` 与 `LC3001` 分别涉及消息到达与采样请求触发，不能预先把两者合并为同一周期。`WDT` 在此是 Watchpoint Definition Table，不是照搬 SMART-QSO 中的硬件看门狗。上述线索来自公开需求文件，仍须以选定基线复核。[W3]

### 2.3 工作区保护

只在独立输出目录和临时检查目录中写文件。不修改 LC 原始源码、需求和测试；不覆盖用户已有文件；不提交、不推送、不改变远程仓库。发现实现问题只记录，除非用户另行要求修复。

## 3. 需求整理：允许补全，但必须区分来源

### 3.1 先盘点，再抽取

先列出选定范围内的正式需求清单及全部原始 ID；将不纳入范围的条目标明理由。不能只挑容易转换的部分，然后以它们作为“全部需求”。

按功能组织中文需求说明，保留原文及术语。在阅读实现后补充文档缺少的行为，但保持“原始文字”和“规范化解释”分栏；冲突不静默修正。

### 3.2 每条需求的最低信息

`requirements.md` 对每条记录至少保存：

| 字段 | 要求 |
|---|---|
| 规范化 ID / 原始 ID | 新增 ID 唯一；NASA 原始 ID 原样保存，一对多拆分要保留父子关系 |
| 需求内容 | 中文说明，明确对象、动作及可观察结果；同时保留支持该表述的短原文或行为描述 |
| 来源类别 | `documented` 文档要求、`code-derived` 代码补充、`design-derived` 设计补充；无充分依据的提议另标 `proposed` |
| 证据 | 文件、版本/commit、原始行范围或页码/章节/表号；代码另加函数或符号 |
| 触发 / 条件 | 区分消息到达、请求到达、周期、状态进入及持续条件 |
| 输入 / 输出 / 状态 | 来源、对象归属、类型与必要的初值或历史状态 |
| 处理 / 约束 | 顺序、分支、边界、次数、时限、失败与禁止行为 |
| 转换关系 | RES、ST 及 ISSUE 引用；表达位置和未保留部分 |
| 评定状态 | 分开记录来源可信程度、映射完整性和实现状态，见第 9 节 |

字段可以放在分组表和条目说明中，不要求挤成一张无法阅读的超宽表。建议新编号使用 `REQ-LC-0001`、`RES-LC-0001`、`ST-LC-0001`、`ISSUE-LC-0001`，也可选另一套一致且无歧义的规则，并在 README 说明。

### 3.3 从代码补需求的具体规则

负责人支持把代码作为补全依据。请检查调用者、分支、返回值、配置、数据结构及测试，提炼“在何种条件下应产生什么效果”，而不是把函数名改写为一句需求。

必须区分活动路径、未接入模块、条件编译分支、仿真桩和测试专用逻辑。源码中定义过某函数，不等于当前配置会调用它。测试用例是补充证据，不是运行通过的替代品。

代码补充可以进入需求清单和有明确标注的规约，不必因为缺少正式文档就丢弃；但它不能自动覆盖与其冲突的正式要求。文档要求尚未实现，也要保留该要求，可以完成需求表达，并把实现状态记为未实现。

### 3.4 拆分与合并

一条原始需求可能同时要求发事件、发请求和更新计数，应保留全部义务及其关系；一个组合语句也可能承担多条需求。不能通过增加拆分条数虚增覆盖率。

不要把每个内存拷贝、私有辅助函数或中间 C 语句都升为独立业务需求。必要的字节序、数据检查、错误恢复等细节，可进入资源能力说明，但必须保留追踪关系。

## 4. 系统资源整理与补全

### 4.1 应当主动补全什么

依据论文第 2 节，将确有依据的信息整理为运行环境/控制器、交互对象、数据元素、算法与协议/端口。来源可包括需求、接口定义、结构体、枚举、配置宏、表定义、算法代码和相关测试。[P1，第 2 节]

| 资源类型 | 必须说明的内容 |
|---|---|
| 运行环境与交互对象 | 角色、边界、提供的能力、调用或消息接口、工作约束、证据 |
| 数据元素 | 名称、含义、方向、类型、单位、范围、初值、写入者/读取者、生命周期 |
| 算法资源 | 输入输出、状态依赖、完整规则、边界与异常情况；公式、流程或伪代码均可 |
| 协议与表资源 | 字段、长度、编码、字节序、校验、有效性规则、失败处理及配置来源 |
| 配置与常量 | 默认值、允许范围、部署可变性和实际选用值；未知即标明未知 |

资源目录必须能解释 `code.rdl` 中出现的名称。只写 `FormulaTable.X` 而没有定义 X 的规则，不算补全。

### 4.2 逻辑接口与物理设备不能混淆

LC 的软件服务、消息端点和数据表，不应为了匹配太阳搜索模板而被虚构为 UART、传感器或物理控制器。先记录其真实角色，再检查所采用 SpaceRDL 版本能否表达。

必要的“软件端点作为外部交互资源”的建模，应明确标为本项目适配方案，给出依据和边界。若论文或已提供语法不足以确认这种适配，把受影响表达列为待确认；不能静默扩展 `Device` 或新造关键字后声称是标准 SpaceRDL。

同理，没有硬件型号、时钟频率或固定周期资料时，不补造 CPU、地址或 `ControlPeriod: 1000ms`。不要把某个循环睡眠值自动当成任务需求中的控制周期。

### 4.3 原始资源与新增定义分开

每条资源标明“原项目已给出 / 根据现有证据整理补全 / 候选定义待确认”。可以起清楚的规约名称，但要保留到原始符号的映射。新名称不代表相应库已经实际部署或能被解析器加载。

资源尚未有正式文件格式时，可以用 Markdown 加结构化 JSON/YAML 作为说明和检查输入，但必须称为本项目资源目录或序列化形式，不能称为论文官方资源库格式。

## 5. SpaceRDL 语法：先核定，再批量生成

这是本次最重要的质量要求。先产生 `grammar_profile.md`，列出“规则、出处、采用写法、适用范围、未决差异”。旧 ZIP、太搜 TXT 和模型记忆都不能代替规则核对。

### 5.1 默认依据与已知差异

主要依据为论文第 3 节表 6、表 7、表 8，并结合第 5.2 节案例。发现差异时保留差异，不把所有写法混在一起。

**本任务建议默认采用表 7 的模板子集**；这是交付约定，不是替论文宣布唯一官方方言。若用户提供了经确认的更新语法或正式解析器，先记录它与论文的差异，再采用经确认的规则。

已经能够从材料定位的差异如下：

| 项目 | 论文模板或说明 | 其他材料 | 处理要求 |
|---|---|---|---|
| 计算引用关键字 | 第 3.3 节、表 7 使用 `ReqCapByFormTable` | 第 5.2 节案例及太搜 TXT 使用 `ReqCapByTable` | 默认表 7；两者是否是解析器别名尚未确认，不混用；改用短写需记录依据 |
| 计算操作 | 表 7 为 `Compute outputdata inputdata …` | 太搜 TXT 使用 `DetAtt`、`CalCtrl` 等功能名 | 不把案例功能名自动认作新基本算子 |
| 协议引用 | 表 7 的 `ProTC`/`ProTM` 模板未附加公式表字段 | 太搜 TXT 和 SMART 示例附加了 `ReqCapByTable ProTable…` | 默认模板子集不这样写；把协议联系保留在资源能力中 |
| 组合时限 | 表 8 将 `[Finished Within T]` 放在组合块之后 | SMART 示例中出现放在左花括号之前的写法 | 按选定模板校正，不因旧检查器放行就照用 |

依据定位：论文 PDF 第 10 页（印刷页 2213）、第 11 页（2214）、第 13 页（2216）；太搜 TXT 第 29、35～39、49～50 行。[P1][P2]

### 5.2 `Compute` 的参数规则

按论文表 7，计算语句的核心顺序是：

```text
Compute 输出数据 输入数据 ReqCapByFormTable 算法条目;
```

仅用于展示语法形状的示意：

```text
Compute outputData inputData ReqCapByFormTable FormulaTable.F1;
```

其中 `outputData`、`inputData`、`FormulaTable.F1` 都是本说明的占位名称，不是已经提炼出的 LC 变量或算法。正式交付时必须换成有定义的实际标识。

**不能无依据地多插入一个函数名参数：**

```text
// 在本任务默认模板下，不采用下面这种多出功能名参数的写法：
Compute EvaluateWatchpoint outputData inputData ReqCapByFormTable FormulaTable.F1;
```

算法功能名称与详细规则放在资源条目中。不得把输入输出写反；读写同一状态时，应明确旧值与新值的关系、隐含状态和副作用。

算法资源不限定为数学公式：论文算法库还接受控制流程和伪代码。因此，不能因为 LC 的处理是逻辑、计数或状态更新，就认为没有数学公式而不能整理成算法资源。[P1，第 2.2 节表 3]

### 5.3 `ReqCapByTable` 不能作为通用后缀

负责人指出的是使用不能随意，不只是关键字长短。论文表 7 只在 `Compute` 模板列出必选的公式表引用字段；本任务默认模板对子系统通信操作不额外添加该字段。

例如，按默认模板可写成以下形状：

```text
GetData deviceName dataName;
SendData deviceName commandData;
ProTC externalName parsedData;
ProTM externalName packedData;
Set stateName value;
```

这些也是模板说明，不是可以不经资源适配直接用于 LC 的业务语句。通信协议、数据格式、校验及重试仍然需要完整定义并关联到资源，不能因为语句不写 `ProTable` 后缀，就把这些要求删除。

**也不能据表 7 推导“所有未来版本绝不允许扩展参数”。本任务只要求：没有确认依据时，不混入扩展语法。**

### 5.4 原子操作与资源能力的分工

`Init` 配置接口，`Set` 更新变量，`GetData` 取数据，`SendData` 输出控制，`ProTC`/`ProTM` 描述对应的外部通信处理，`Compute` 引用算法完成数据处理。[P1，表 5、表 7]

一个资源能力可能包括发送取数请求、等待、接收、校验等步骤，不必把它强拆成新算子。反过来，独立的业务判断、连续计数、模式变更和错误分支，不能靠模糊的资源名称全部隐藏。

“代码在发送消息”不自动意味着必须选 `ProTM`；“接收消息”也不自动意味着 `ProTC`。应根据交互对象和需求语义决定，并记录逻辑接口适配是否得到支持。

### 5.5 时间与任务结构

论文表 6 区分 `At(t)`、`At(t, period)`、`Finished Within T` 和 `Over(T, c/nc, n)`；表 8 还涉及顺序组合中的间隔约束。必须查清触发、时长、次数以及参考时刻，不能按英文词面自行解释 `In`、`After`。[P1，表 6、表 8]

不默认认为 `At(0, 60000ms)` 已被该语言定义为任意多周期调度；应先确认实际语法。`AppTask` 在论文中有周期任务含义，消息到达也不等于硬件中断。因此 LC 的事件驱动行为不能生硬塞入固定周期或 `InterruptTask`。

若现有语法不能忠实表达某类触发或非周期平台：先用自然语言和资源/行为表完整保存需求，把涉及的正式语句标为待表达，并给出最小适配建议；不虚构周期，不把自造 `OnMessage` 等关键字混入 `code.rdl`。无影响部分继续转换。

所有时间约束必须保留适用对象、起算点、单位及严格/非严格边界。单个操作时限与所在组合块预算要能解释；算法的循环总时限与单次迭代时限有疑义时登记，不悄悄择一。

### 5.6 语法不确定时如何继续

先完成确定的需求、资源与追踪工作；仅隔离受影响的语句。把无法由资料解决的问题集中在一个清单中向用户确认，不逐条反复打断。没有正式解析器时，允许完成候选规约，但必须说明“按已记录模板人工/静态核对”，不能声称通过官方语法验证。

## 6. 需求到语句：必须保留的语义

每个转换都需要检查：对象是谁、条件是什么、输入输出怎样流动、引用规则是什么、何时触发、失败时怎样处理、哪些情况禁止动作。

重点检查以下情况，均是本次新增的审查规则，不是对 LC 已发现缺陷的宣告：

- 阈值、比较方向和边界不能变；连续次数不能变成累计次数，持续条件不能变成一次满足。
- 应用级状态与某个条目的状态不能混成一个变量；不同结果枚举不能无依据压成 True/False。
- 禁用、被动、无效、过期、错误等情况应依选定基线分别处理，不给未知数据擅自填正常值。
- 数据计算、状态提交、发出请求、外部执行及完成确认不是同一动作；只声称证据支持的结果。
- 可配置参数应进入相应计算或触发规则，不能一边提供“修改参数”操作，一边在业务语句中写死另一个常量。
- 资源和语句中的单位、大小写、数组维度、索引范围、符号名要一致；默认值、示例值和当前配置值要区分。
- 输出使用之前有来源，历史状态有初始化与更新；错误返回值、未收到消息等路径不能只写在注释里而遗漏行为。
- 条件充分但代码尚未实现的正式需求仍可描述；映射完整性与实际实现状态分开评价。

`code.rdl` 中可用注释标记 ST-ID 和 REQ-ID，但不要为了追踪而新增未经定义的语言关键字。不能用整段 `...` 或未定义函数替代核心处理并记为完整映射。

## 7. 必须提供一个完整贯通的 LC 例子

在 `walkthrough.md` 中选择一组有原始依据的需求，按以下顺序说明：

> 接收到相关数据 → 形成检查结果 → 收到后续评估请求 → 根据状态和计数判断 → 发出或抑制相应请求 → 更新结果并报告。

这是例子组织方向，不是强制 LC 每次收到数据都立即触发所有动作。具体触发和顺序必须来自选定基线，尤其不要把不同入口并成一个循环。

贯通讲解至少包含：原始需求 ID 和短原文、规范化需求、资源定义、实际 `code.rdl` 的对应片段、逐段人话解释、输入输出/状态衔接、正常路径与一条被禁止或失败的路径。

优先使用项目现有表或测试中的参数；采用自拟数值时明确标为教学场景，不能冒充原需求。没有运行程序的例子称为纸面走查，不称为测试结果。

例子的“闭环”是从需求、输入、判断、动作到结果记录的可追踪处理链，不应被说成已经证明整颗卫星恢复安全。该例子用来检查前后衔接，不替代全量需求整理。

## 9. 状态与覆盖统计：不要再用一个 `verified` 混淆多种含义

以下为本次交付的评价约定，可保留旧字段作为兼容列，但必须给出这几个相互独立的维度：

| 维度 | 建议分类 | 含义 |
|---|---|---|
| 来源 | documented / code-derived / design-derived / proposed | 信息从哪里来；不是正确性排名 |
| 语义映射 | full / partial / none | 原需求的全部义务是否有忠实表达；有遗漏就是 partial |
| 表达形式 | statement / resource / constraint / mixed / documentation-only | 要求被放在哪里；单纯注释不算机器可检查约束 |
| 语法核对 | checked / pending / failed | 相对于哪份语法 profile，哪些部分已检查 |
| 实现证据 | supported / not-implemented / conflict / unknown | 代码对要求的支持情况；supported 也不等于运行验证通过 |
| 检查层次 | static / manual / executed-test / not-run | 实际做了哪种验证，不用含糊的“已验证”替代 |

来源清楚但实现冲突的条目，映射也可能是 full；只写出一条语句却漏掉持续条件的条目，映射必须是 partial。算法资源完整且引用准确可以参与 full 的判断，不能只按正文行数判定。

统计至少分别报告：正式需求条数及纳入范围、代码/设计补充条数、规范化需求条数、full/partial/none 条数、仅注释保留的条数、原子和组合 ST 数、资源数、开放问题数。

正式需求覆盖率以范围内的原始 ID 为分母；拆分后的所有必要子义务都覆盖，原始 ID 才能记为 full。代码补充需求单独统计，不能用大量补充条目冲高正式需求覆盖率。若只完成部分材料，注明范围和未阅读部分，不声称全项目覆盖。

语法、资源适配、语义映射、实现、测试分别给总体状态。缺少正式解析器或存在重要未决语法时，只能报告候选规约或部分完成。

## 10. 检查要求与报告方式

### 10.1 可自动检查的内容

脚本至少检查：文件齐全、ID 唯一、引用存在、REQ/RES/ST/ISSUE 链接一致、statements 与 code 片段相符、行号范围有效、资源与数据标识已定义、数量统计可复算、源文件哈希一致。

基于 `grammar_profile.md` 增加确实能够实现的语法子集检查：括号、分号、基本算子的参数角色、Compute 的额外功能名误插入、引用字段使用范围、组合时限位置等。未支持的结构必须报告为未检查，不能静默算通过。

检查器规则必须有外部语法依据。不能先写错规约，再修改自制检查器让它通过；也不能用仅检查括号的工具证明参数、时间语义正确。

### 10.2 必须做的人工语义核对

逐条核对条件、边界、连续性、消息/周期关系、数据来源、资源能力展开、异常路径和动作抑制。记录覆盖了哪些 REQ/ST、证据和结果。第 6 节所列项目不能只用一次正则检查替代。

论文自身或不同参考文件的冲突，不由模型静默消解；疑似实现差异先检查版本、配置、层次和单位。不同层级的两个数字不必然冲突。

### 10.3 检查器要有反例

在独立测试样例中故意放入额外 Compute 参数、无定义资源、错误 ISSUE 引用、语句表与正文不一致等情况，确认检查器会报错。不能只测试正确输入。

对于遗漏持续条件、时序预算不兼容等不能自动判断的问题，明确由人工走查覆盖；不要虚报检查器具备这些能力。

### 10.4 原项目测试不是必需的环境重建任务

环境就绪且成本合理时，可运行所选版本的 LC 相关测试并保存输出；不要求为本次需求整理重建整套飞行环境。未执行、执行失败、缺依赖都如实记录。

原项目单元测试通过，只说明那些测试的结果，不能据此判定 SpaceRDL 与需求等价。纸面例子、静态检查和真实执行记录分开。

### 10.5 报告必须能复现

`validation_report.md` 写明检查范围、命令、工作目录、工具版本、时间、退出码、测试结果和剩余限制。实际使用的脚本和日志要随包提供；只有 README 写“0 error/0 warning”而没有脚本和运行证据，不算完成检查。

## 11. 执行顺序与中途交接

**阶段 A：建立依据。**读取本交接文档、负责人反馈、论文语法和旧包结构；定位 LC 正式需求与代码，固定基线和范围；产生 source manifest 与 grammar profile 的初稿。

**阶段 B：整理需求和资源。**先完成正式需求盘点，再结合设计和代码补充；补齐算法、数据、协议和交互边界。未知信息定位到问题，不以项目缺少现成资源库为理由省略这一步。

**阶段 C：先做一个贯通样例。**选择第 7 节的处理链，校准 Compute、引用字段和事件驱动适配。发现有争议的语法先局部隔离，不把问题批量复制到全项目。

**阶段 D：扩展到范围内其余需求。**生成七个主文件、追踪关系和完整例子。全部数值和结论回链到依据，补全各项状态。

**阶段 E：核对与打包。**运行检查器和反例测试，做人工语义复查；根据结果修改本次产物，不修改原工程；最终重新计算行号、哈希和统计，生成 ZIP。

有资料无法访问时，先登记缺失并完成不受影响部分。需要用户裁决的关键问题集中提出；不要为了避免提问而编造协议、算法或语法。中途中断时保存阶段、已处理文件/需求、待办与未决问题，保证可继续。

## 12. 最终交付与验收清单

输出目录建议为 `lc_spacerdl/`，ZIP 为 `lc_spacerdl.zip`。ZIP 内只有一个清晰根目录，保留相对路径；不得包含 `.git/`、虚拟环境、缓存、密钥、无关用户资料或大批编译产物。

交付前解压到新目录验证：文件可读、相对链接可用、检查命令可执行或能够明确报告环境依赖、证据定位可复核。对最终 ZIP 计算 SHA-256，并在最终交付消息中给出。

### 验收项目

- [ ] 七个主文件均有实际内容，语法、来源、检查和贯通例子等辅助文件齐全。
- [ ] LC 版本已固定，原始需求 ID 保留，正式要求和代码补充清楚区分。
- [ ] 未实现的文档要求没有被删除，代码已有行为没有被一概拒绝整理。
- [ ] 资源不是只有名称，算法、数据与协议有完整或明确标注缺口的定义。
- [ ] Compute 参数、公式表引用及组合语法按 profile 核对；没有偷偷混入自造方言。
- [ ] 事件驱动、逻辑接口等适配没有伪装成论文已定义的物理/周期模型。
- [ ] 映射没有遗漏条件、持续时间、禁止动作和错误分支；不完整项如实标 partial。
- [ ] 所有 REQ/RES/ST/ISSUE 引用有效，规约与语句表一致，行号属于最终版本。
- [ ] 覆盖统计分母明确、可以复算，没有拿语句数或文件齐全证明需求完整。
- [ ] 检查脚本、反例、日志和报告随包交付；没有把未运行项目写成通过。
- [ ] 有一条从需求到资源、语句、数据和结果的完整讲解链。
- [ ] ZIP 不依赖执行者私人路径；没有修改 LC 原项目；遗留问题明确。

交付给用户时只需简要说明：所选基线、做了哪些工作、三类来源需求的数量、full/partial/none 数量、实际检查结果、最重要的未决问题、ZIP 位置。详细信息放在文件中，不再在聊天中粘贴整套文档。

**“完整交付包”是产物和证据链齐全，不是承诺所有需求已解决。允许如实标注的部分完成，不允许用占位、注释和宽松检查器伪装成全部完成。**
