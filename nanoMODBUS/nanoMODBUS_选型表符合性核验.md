## 3 需限定或修正的表述

### 3.1 「串口或 TCP 数据流」——库不实现线路，应判定为「需由宿主提供」

选型表把「串口或 TCP 数据流」列为功能要点，但本库对数据流**只定义一层契约**：宿主必须实现 `read`/`write` 两个回调（按「读满/写满或字节超时」阻塞语义工作，返回值区分完成/超时/传输错），可选实现 `crc_calc`/`flush`（`nanomodbus.h:161-172`、`nanomodbus.c:147-166`、§2.4 `NMB-IREQ8`/`NMB-IREQ9`）。

库自身不含：串口波特率与数据位配置、RS-485 收发方向切换、TCP 连接建立/关闭/保活、规范中 3.5 字符静默间隔检测，也不提供加密与访问控制（`NMB-IREQ12`（1）–（5））。随仓 `examples/`（31 文件 3,421 行）是各平台的宿主实现示范，按范围档**不写成需求**（§1.2、勘测报告 §7）。

建议该字段改判为「**串口或 TCP 数据流（需由宿主提供；本库只定义字节流读写回调契约）**」。此结论已写在正文 `NMB-IREQ12`（7），可作为判定依据直接引用。

### 3.2 「运行状态」——库无状态机与状态输出接口

选型表写的三个状态词都能在源码中找到实现痕迹，但没有一个是**定义过的状态**：

| 选型表状态 | 实现载体 | 可观测性 |
| --- | --- | --- |
| Modbus RTU/TCP | 创建实例时由 `nmbs_platform_conf.transport` 一次性指定（`nanomodbus.h:162`、`nanomodbus.c:240`），此后不可切换 | 仅实例内字段 |
| 客户端请求 | 各客户端 API 同步走「组装请求 → 发送 → 收响应 → 六道校验」（§3.4 `NMB-FREQ3-1`） | 无状态位；仅返回值 |
| 服务器响应 | `nmbs_server_poll()` 每调用一次最多处理一帧，处理完立即返回（§2.1（3）、§3.10 `NMB-FREQ9-2`） | 无状态位；返回值区分成功/超时/错误 |
| 功能码处理 | `handle_req_fc()` 的 `switch` 分发到 12 个功能码分支（§3.10 `NMB-FREQ9-3`、附录1.1） | 无状态位；异常以应答报文体现 |

结论与建议：状态词可保留（对应真实运行阶段），但若下游要按状态机集成或做状态上报，必须知道**库不输出状态、不提供状态查询 API、角色与传输在创建后固定**，并需由宿主在轮询循环中驱动服务器侧（§2.1（3）–（7））。建议该字段后加括注「（库无状态机，状态为角色与轮询驱动的推导量）」。

### 3.3 「外设」——无电气外设，代码侧是回调契约

本库不是固件：无 `main()`、无硬件驱动、无外设控制（元信息表「软件性质」、§1.5）。选型表「生成 Modbus 请求/响应，并调用应用映射的寄存器读写接口」在代码侧的准确载体是两张回调表——平台回调（字节流 I/O）与 12 个服务器回调（`nmbs_callbacks`，`nanomodbus.h:182-241`）；寄存器地址空间是否存在、如何映射到设备，**完全由宿主回调决定**，库不做应用层语义校验（`NMB-IREQ12`（5））。

「不直接控制执行器」成立且强于选型表表述：库内不存在任何引脚、寄存器地址或设备对象。建议该字段改判为「**无电气外设；对外仅提供数据流回调与应用寄存器回调接口，由宿主映射到设备**」。

### 3.4 「异常」——三类错误不在同一层，需分开表述

选型表把「CRC 或报文校验错误」「非法功能码」「非法地址」并列为异常，但实现分三层处理：

| 情形 | 实现层 | 对外表现 | 证据 |
| --- | --- | --- | --- |
| CRC 错误 / MBAP 协议号与长度非法 / 报文不完整 | 传输校验 | **库错误码（负值）**，且**不发送任何应答**；`nmbs_server_poll()` 原样返回该负值 | §3.18（6）、`nanomodbus.c:299-315`、`371-382` |
| 非法功能码（本机寻址或 TCP 模式下） | 协议层 | Modbus **异常码 1** 应答（广播或非本机地址时不发应答） | §3.10 `NMB-FREQ9-3`（4）、`nanomodbus.c:1885-1888` |
| 非法地址（`address + quantity > 0x10000`） | 协议层 | Modbus **异常码 2** 应答 | §3.11（3）、§3.12（3）（5）（6） |
| 应用回调返回错误 | 应用层 | 返回值 1..4 原样转成异常码；其它非零值统一转异常码 4 | `NMB-IREQ10`（5） |

即：「协议异常响应」与「接口错误状态」在本库中是**两条不同的返回路径**（前者是线上应答，后者是 API 返回值），选型表「返回协议异常或接口错误」的并列表述成立，但下游若按「异常即应答」理解会与实现不符。建议补注「协议异常经应答报文返回；传输与校验类错误以库错误码返回且不应答」。

### 3.5 「非法地址」的实现口径——库只判范围，不判存在性

库内对地址的校验仅为 32 位无符号运算 `address + quantity > 0x10000`（§3.11（3）、§3.12（3））；**寄存器地址是否真实存在、可否读写，属于宿主回调的职责**，库不做检查（`NMB-IREQ12`（5））。另有服务器侧只判「功能码已编译进来但回调字段为空」的路径，返回异常码 1（`NMB-IREQ10`（6））。选型表「非法地址」的措辞按协议术语无误，但需按上述口径限定，避免被读成「库内置地址空间管理」。

### 3.6 第 11 字段「B 级 + Star 数」——非功能判定，不能由源码核验

- **「B（技术文档评级，非完整 SRS）」**：这是对上游**资料形态**的评级，不是对实现功能的判定。就资料面核对：上游对外资料为 `README.md`（204 行）、由 `Doxyfile` 从源码生成的 API 文档站、Releases 页与 `tests/`，**确无正式软件需求规格说明书**，故「非完整 SRS」成立。但本次逆向交付物本身已是完整 SRS 形态：2,101 行、77 个需求块（FREQ 48 + IREQ 15 + PREQ 7 + SREQ 7）、878 条可解析引用、0 条可疑（阶段 E 核验）。评级字段不影响本交付物的完整性判定。
- **「约 887 Star」**：属外部动态量。核验时点（2026-10-19）经 GitHub REST API 实测为 **923 Star / 242 Fork**（`https://api.github.com/repos/debevv/nanoMODBUS`，`stargazers_count: 923`、`forks_count: 242`）。原表 887 为上一轮检索值，差异属正常增长，非描述错误。建议该字段标注检索时点，不作为符合性判定项。

### 3.7 「规模：小型」——可量化支撑

- 核心有效代码行 1,976（`nanomodbus.c` 1,806 + `nanomodbus.h` 170），与上游自述「约 2000 行」吻合（元信息表「有效代码行」行、勘测报告 §2）；
- 逆向范围 5,059 行（核心 3,024 + `tests/` 2,035）；全仓 9,003 行 / 51 文件；
- 资源侧：报文缓冲固定 260 字节、位域默认 2000 位、全库**无动态内存分配**（全仓 `.c` 无 `malloc/calloc/realloc/free`，勘测报告 C4、§3.17 `NMB-PREQ`）。

## 4 综合判定

选型表 nanoMODBUS 行**描述与实现一致**，需在选型表侧补注的口径共 5 处：①「串口或 TCP 数据流」需由宿主提供；②运行状态无状态机与状态输出；③外设实为回调契约而非电气对象；④异常需区分「协议异常应答」与「库错误码返回」两条路径；⑤「非法地址」仅指地址范围判定。这 5 处均已在规格书正文（`NMB-IREQ8`–`NMB-IREQ12`、§3.11、§3.18）与附录 1 登记，**不构成对选型表描述有效性的否定**。

- 「工业 Modbus 协议」有实现证据：12 个功能码（01/02/03/04/05/06/15/16/20/21/23/43）+ 1 条非法功能码路径，RTU/TCP 双传输，客户端与服务器双角色（元信息表、附录1.1、§3.3）；
- 「小型」有量化证据：有效 1,976 行、静态内存、无运行时第三方依赖（§3.17、附录2.3）；
- 未发现选型表存在与实现相矛盾的功能性描述；未发现「不支持」字段。

**遗留与建议**：第 11 字段的评级与 Star 数建议在选型表中与功能字段分开表述（评级 + 检索时点），以免与 1–10 字段的符合性判定混同。
