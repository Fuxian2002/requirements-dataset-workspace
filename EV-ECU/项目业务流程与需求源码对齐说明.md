## 1. 项目范围与当前基线

EV-ECU 是面向电动车辆的嵌入式控制器固件。主要业务是采集驾驶输入及车辆状态，执行车辆状态机和故障判断，经 CAN 控制逆变器，并提供电池状态接收、低压设备控制和维护通信。

- 当前需求文档：[Word](EV-ECU_v4_需求规格说明书.docx) / [PDF](EV-ECU_v4_需求规格说明书.pdf)。
- 项目目录：ev-ecu-master（`ev-ecu-master`），主要业务实现位于 firmware/src（`ev-ecu-master/firmware/src`）。
- 固定源码：EV-ECU_v3_源码快照.zip（`EV-ECU_v3_源码快照.zip`）。V4 仅修订文档，继续使用这份 V3 命名的源码基线。
- 需求共 58 条：38 条功能、8 条接口、6 条性能、6 条可靠性和安全性需求。

需求以本地封存源码为依据，不以 README 的规划描述或当前公开 master 代替实际实现。硬件文件用于理解控制对象，不意味着已核验全部电路或完成整车安全认证。

## 2. 设备与信号关系

```text
踏板、制动压力、按钮、SDC → ECU 状态采集与故障判断
                              ↓
Orion BMS ── CAN2 ──→ 车辆状态机与扭矩控制 ── CAN1 ──→ 逆变器 → 电机
                              ↓
                      PDM / 仪表输出 / PC 维护接口
```

| 设备或资源 | 业务用途 | 实现对应与边界 |
| --- | --- | --- |
| STM32F767 + FreeRTOS | 运行控制任务、设备驱动和共享状态 | `hal/stm32f767`、`vcu/startup`、`system-lib` |
| 双路加速踏板、前后制动压力 | 驾驶意图及合理性判断 | ADC1 DMA 索引 8/9/10/11；`discretesense` 与故障管理 |
| 仪表按钮、SDC 输入 | 状态转换请求和停机链状态 | GPIO 输入/中断、状态机和 `sdc` |
| Cascadia 逆变器与电机 | 扭矩执行和逆变器状态反馈 | CAN1；`cInverter.c` |
| Orion BMS | 提供电池测量与状态 | CAN2；`orionBms.c`；不是本 ECU 内部的电芯管理算法 |
| PDM | 低压支路输出控制 | 6 路输出；`pdm.c` |
| 轮速输入 | 轮速计算 | TIM3 路径存在，但初始化未启动相应定时器，不能声称采集链已完整运行 |
| GPS、PC 维护端 | 定位数据、配置/调试通信 | USART6 9600；USART1/3 115200；维护接口不是安全认证接口 |

CAN3 虽被配置，不能据此虚构一个已经接入的业务设备。文件路径和默认通道映射见 `vcu/vehicleInterface/config/deviceMapping.h`。

## 3. 整体业务流程及实际受阻点

### 3.1 上电与运行组织

`ECU_Init_Task` 依次建立系统、板级外设和设备，载入默认配置，建立车辆状态和控制接口，启动业务任务，最后删除初始化任务。配置载入当前使用 `DefaultConfigData`，不能把 EEPROM 持久化配置视为已经完成。

初始化后，采集任务更新共享车辆状态；状态机决定车辆阶段和控制许可；扭矩任务将加速请求映射到控制命令；设备任务负责 CAN/UART 等通信。它们是并行调度的工作链，不是每一帧严格顺序执行的一条同步函数链。

### 3.2 状态机的代码逻辑

在所需对象正确绑定、任务能够执行的前提下，源码定义了以下主要转换：

1. `INIT → LV_STARTUP → LV_READY`：完成启动并按故障状态判断是否进入低压就绪。
2. `LV_READY → HV_ACTIVE`：按钮上升沿触发请求，并清除相应 ECU 错误输出。
3. `HV_ACTIVE → HV_CHARGING`：等待至少 500 ms 后执行逆变器使能。
4. `HV_CHARGING → ACTIVE_NEUTRAL`：逆变器状态达到 READY；状态可读路径中的等待超过 7000 ms 可转入 FAULT，不能将其概括为所有路径均有统一超时保障。
5. `ACTIVE_NEUTRAL ↔ ACTIVE_FORWARD`：由按钮上升沿控制，伴随方向和扭矩许可变化。
6. 正常启动后的故障路径可转入 `FAULT`；进入后的执行步骤禁用扭矩并设置 ECU 错误输出，没有自动恢复出口，也不等于直接执行了逆变器断电或高压放电。

**上述逻辑存在明确集成阻断。** `VSM_Init` 没有给 `FaultManager.vehicleData` 赋值；`FaultManager_Step` 使用该字段调用 `VehicleState_CopyState`，可能在首次执行发生空指针访问。因此需求文档可以说明“源码定义了这些转换”，但不能据此声称当前默认初始化路径已经实现可运行的完整整车状态机。

### 3.3 驾驶输入、故障与扭矩输出

采集结果进入共享状态后，故障管理检查踏板/制动等条件及持续计数。部分故障检查还是占位返回值，电池失败状态也不是全部映射为有效故障策略。BMS 默认阈值为 `750 / 4500 / 420 / 1000`，与比较所用物理量存在尺度问题；最低 SOC 是 **1000**，不是 100，不能用“合理的设计值”覆盖实际源码值。

扭矩任务按周期读取加速请求，经映射插值进入车辆控制接口。未允许扭矩、方向未知等情况应输出零扭矩。逆变器命令使用 0.1 Nm 编码；`SendCANCommand` 将 `speed=0`、`speedModeEnabled=0`、`torqueLim=0`，当前未使用速度控制，扭矩上限选择逆变器内部参数。使能函数对发送结果的合并存在掩盖失败的风险，本地使能标志不构成硬件已接受命令的证明。

## 4. 任务与调度关系

| 工作任务 | 调度/输入 | 输出与需求含义 |
| --- | --- | --- |
| 初始化 | 启动时一次执行 | 建立对象、设备和任务；区分已实现与 TODO |
| 状态管理、扭矩、踏板等周期工作 | 100 Hz 通知，名义周期 10 ms | 状态转换、故障判断、驾驶请求与控制命令 |
| 逆变器、BMS 和 PC 通信处理 | 周期任务结合接收队列/中断 | 解析设备反馈、发送控制和维护消息 |
| 轮速统计、PC 周期上报 | 部分处理每 100 次通知执行，名义 1 Hz | 不能把名义频率当成真实采样已验证；轮速还有启动缺口 |
| LED 指示 | 名义每 1 s 翻转 | 完整亮灭周期约 2 s，不是硬件看门狗证明 |

任务通知可能合并，不能默认发生延迟后会逐个补跑所有丢失周期。中断、队列、共享状态锁与任务上下文的区分，是接口和可靠性需求的一部分。
